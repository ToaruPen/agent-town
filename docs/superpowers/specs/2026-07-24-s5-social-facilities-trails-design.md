# S5 制度起点の施設と小道 設計仕様書

日付: 2026-07-24  
ステータス: 設計承認済み・文書レビュー待ち

## 1. 目的

社会制度が成立しても、地図に文章だけが増えるのでは街は変わらない。制度が資材と労働を集め、施設を建て、住民の移動と生活を変えて初めて、社会の成立が空間として見える。

S5では、実装済みの食料不安、集団、制度を建設と往来へ接続する。共同備蓄、私的取引、配給統制の三制度は、それぞれ共同穀倉、穀物市場、配給所を必要とする。住民が施設を建てて利用し、繰り返された移動が踏み跡と小道を残す。

完成した街並みは結果である。プレイヤーは施設を直接配置せず、次の因果を観察する。

> 欠乏と記憶  
> → 食料不安  
> → 支持と反対  
> → 制度成立  
> → 施設需要  
> → 敷地選定  
> → 資材搬入と建設  
> → 運用と住民生活への効果  
> → 往来と小道  
> → 新たな欲求と制度支持

## 2. スコープ

### 2.1 実装対象

- 三つの制度に対応する専用施設
  - 共同備蓄 → 共同穀倉
  - 私的取引 → 穀物市場
  - 配給統制 → 配給所
- 社会的な必要を建設へ渡す共通の空間需要契約
- 施設ごとの決定論的な敷地選定
- 木材の確保、搬入、建設、完成、稼働
- 施設位置に結び付いた食料在庫と利用
- 各施設固有の恩恵、負担、失敗状態
- 実際の移動から生じる通行量、踏み跡、小道
- 施設、道、住民から因果をたどる観察UI
- 通常速度で5分を目安、10分を上限として、最初の施設稼働と小道化が見える調整

### 2.2 今回は実装しないもの

- 住居、工房、寺院、防壁など、食料制度以外の需要発生ロジック
- 個人財産、通貨、価格形成、商人個体、荷車
- 制度の廃止、施設の転用、破壊、再建
- 石畳や舗装路など、制度投資による人工道路
- プレイヤーによる承認、配置、建設命令
- LLMによる敷地選定、建設判断、運用判断

空間需要の型と建設境界は、将来の施設種別にも使える形で定義する。今回動かす発生源は制度だけであり、未実装の施設挙動を先回りして作らない。

## 3. 成功条件

同じseedと同じ入力から、制度、施設種別、敷地、建設経過、小道が一致することを前提とする。そのうえで、次を満たす。

1. 成立した食料制度が、対応する施設需要を一度だけ発生させる。
2. 住民が木材を施設予定地へ運び、建設作業を行う。
3. 完成した施設が実在庫と住民行動を通じて効果を発揮する。
4. 恩恵だけでなく、維持労働、資源消費、変動、疲弊のいずれかが発生する。
5. 施設への反復移動が同じ経路へ集中し、踏み跡から小道へ成長する。
6. 小道は移動を速め、使われなければ徐々に薄れる。
7. 施設と小道を選ぶと、成立理由、利用、効果、負担を確認できる。
8. 三制度それぞれの決定論的fixtureで、`TICK_RATE * 60 * 10`を上限として施設稼働と最初の小道化へ到達する。調整上の目安は5分とする。

## 4. 共通の社会的建設契約

施設を生む理由は一つではない。世帯は住居を求め、生業は工房を求め、信仰は祠を求め、外敵は柵を求める。発生源が違っても、建設へ渡す情報は共通化できる。

```ts
type SpatialDemandSource =
  | { kind: "household"; id: string }
  | { kind: "livelihood"; id: string }
  | { kind: "institution"; id: string }
  | { kind: "faith"; id: string }
  | { kind: "externalPressure"; id: string };

interface SpatialDemand {
  id: string;
  facilityKind: FacilityKind;
  source: SpatialDemandSource;
  supporterIds: string[];
  requiredWood: number;
  requiredLabor: number;
  status: "seekingSite" | "awaitingMaterials" | "building" | "fulfilled" | "blocked";
  blockedReason: "noValidSite" | null;
  site: Position | null;
  siteRationale: SiteRationale | null;
  provenance: Provenance;
}
```

`SpatialDemand`は建物そのものではない。「誰が、何を必要とし、何を負担するか」を保存する要求である。有効な敷地がなくても消えず、`blocked`として理由を保持する。

S5で生成する`source.kind`は`institution`だけとする。型の他variantは将来の接続点であり、今回のシミュレーション分岐には入れない。

## 5. 建物と施設の状態

既存の`House`だけを格納する建物配列は、判別可能なunionへ拡張する。

```ts
type Building = House | Facility;

type FacilityKind = "communalGranary" | "grainMarket" | "rationDepot";

type FacilityBlockedReason =
  | "unreachable"
  | "full"
  | "noTradeRoute"
  | "maintenanceOverdue";

interface Facility {
  kind: FacilityKind;
  id: string;
  demandId: string;
  institutionId: string;
  pos: Position;
  progress: number;
  complete: boolean;
  woodDelivered: number;
  inventory: { wood: number; food: number };
  operation: "inactive" | "active" | "blocked";
  blockedReason: FacilityBlockedReason | null;
  visitsToday: number;
  maintenanceDue: number;
  siteRationale: SiteRationale;
  provenance: Provenance;
}
```

`House`はS5でも既存の人口圧力から建つ。配置判断を`SpatialDemand`へ移す作業は後続スライスへ残すが、描画、占有判定、建設対象の検索は`Building` unionを扱う。施設だけを別の隠し配列へ置かない。

`WorldState`には`spatialDemands`と後述する`trailCells`を加える。`trailCells`は`tiles`と同じrow-major配列で、長さは`width * height`とする。wire protocolはwelcomeとupdateの両方で状態を運び、クライアントは独自のゲーム状態を作らない。

## 6. 制度から施設需要への変換

成立済み制度に対応する未充足需要がなければ、安定したIDを持つ需要を生成する。

| 制度 | 施設 | 主な立地条件 |
|---|---|---|
| `communalGranaryStore` | `communalGranary` | 食料採集地と住居の双方へ届きやすく、既存備蓄に近い |
| `grainMarket` | `grainMarket` | 既存の往来、集落入口、滞留可能な空地へ近い |
| `rationControl` | `rationDepot` | 人口重心に近く、到達距離の住民間格差が小さい |

需要IDは制度IDから導出する。同じ制度が複数tickにわたって観測されても、需要と施設を重複生成しない。

## 7. 敷地選定

候補地は、マップ内、歩行可能、資源なし、既存建物と備蓄地点に非重複、少なくとも一人が到達可能、という共通条件を満たすタイルから選ぶ。

候補ごとに距離、到達性、空地、既存交通、人口分布を採点する。施設固有の重みは`packages/shared/src/constants.ts`に置き、サーバー実装へ数値を埋め込まない。

```ts
interface SiteRationale {
  score: number;
  contributions: {
    factor: SiteFactor;
    value: number;
    weightedScore: number;
  }[];
}
```

`SiteFactor`は`foodAccess`、`residentAccess`、`stockpileAccess`、`existingTraffic`、`settlementEdgeAccess`、`openSpace`、`accessEquality`のunionとする。未使用の要因を0点で並べず、実際に採点した要因だけを`contributions`へ保存する。

UIには最終地点の上位評価要因を表示する。全候補の詳細は保存しない。同点はseed付き乱数と座標順で決着させ、列挙順やオブジェクトの挿入順へ依存させない。

候補がなければ需要を`blocked`にし、地図や建物状態が変わった更新間隔で再評価する。毎tick全マップを採点しない。

## 8. 資材搬入と建設

施設は木材が予定地へ届く前に建設進捗を得ない。

1. 需要が敷地を確定し、未完成の`Facility`を予定地へ作る。
2. 木材が備蓄にある場合だけ、住民へ一運搬量ずつ搬入タスクを割り当てる。
3. 住民が備蓄地点で木材を受け取る。この時点で備蓄を減らし、住民の携行量を増やす。
4. `woodDelivered`が必要量へ達すると建設作業が可能になる。
5. 住民の作業が`progress`を増やし、必要労働へ達すると完成する。
6. 完成後の初期在庫と運用状態を設定する。

木材を事前予約する隠し在庫は作らない。木材は、備蓄、運搬中の住民、施設予定地のいずれかに存在する。運搬が中断された住民は、荷を予定地か備蓄へ戻す。複数の住民が同時に受取を試みる場合は、安定したagent ID順で処理し、残量を下回る受取を拒否する。

飢え、休息、凍死回避などの生存割り込みは建設より優先する。建設が遅れても住民の生存判断を無効化しない。

## 9. 施設運用

開拓時備蓄は施設完成までの仮置場として残す。施設完成後、食料の預入、受取、食事、維持作業の目的地が制度方針に従って変わる。画面上の補正だけで効果を与えない。

すべての食料在庫は日境界で腐敗を処理する。開拓時備蓄、穀物市場、配給所には共有の基準腐敗率を使い、維持された共同穀倉だけが低い腐敗率を使う。腐敗量は在庫から実際に差し引き、施設の日次実績へ記録する。

### 9.1 共同穀倉

共同穀倉は食料を保護し、欠乏時の予備を持つ。

- 食料を施設在庫へ搬入する。
- 開拓時備蓄より低い日次腐敗率を適用する。
- 安全日数を上回る間は一定量を非常用として保持する。
- 食料日数が閾値を下回ると、支持者に限定せず全住民へ放出する。
- 定期的な維持作業を要求し、未実施なら保護効果を弱める。

大きな初期木材と維持労働が代償となる。非常用在庫は平時の自由消費から外れるため、目先の余剰を減らす。

### 9.2 穀物市場

穀物市場は、余剰と不足を外部交易へ接続する。

- 住民が食料と交換用木材を市場へ搬入する。
- 出身国の都市が世界地図上の交易路へ接続している場合だけ、市日を開ける。
- 食料日数が不足閾値を下回れば、木材を支払って食料を輸入する。
- 食料日数が余剰閾値を上回れば、上限付きで食料を輸出し木材を得る。
- 交換率、取引間隔、輸出上限は共有定数とする。

取引では、支払資源を減らしてから受取資源を増やす。交易路がなければ市場は`blocked`となり、食料や木材を生成しない。個人価格と貨幣は扱わず、集落単位の物々交換として記録する。

### 9.3 配給所

配給所は不足時の消費を抑え、飢えの深い住民を優先する。

- 食料日数が閾値を下回ると配給を開始する。
- 食事対象は、飢えの深さ、健康、前回配給時刻、安定したID順で決める。
- 通常食より少ない食料で、通常より小さい飢え回復を与える。
- 配給を減らされた、または待たされた住民へ`rationStrain`を蓄積する。
- `rationStrain`は配給統制への支持を直接下げ、配給終了後にゆっくり回復する。

配給は食料を伸ばすが、住民を満腹にはしない。飢餓死亡の抑制と統制への反発が同じ処理から生じる。

### 9.4 食料保存則

集落内の食料総量は、次の操作だけで変わる。

- 採集または交易による流入
- 食事、腐敗、交易による流出
- 在庫間の移動

在庫間移動では総量が変わらない。施設効果を検証するテストは、操作前後の総量と変化理由を照合する。

## 10. 通行量と小道

道は建設完了イベントから自動生成しない。住民が一タイル進むたび、移動目的に応じた通行量をそのタイルへ加算する。

```ts
type MovementPurpose =
  | "survival"
  | "gathering"
  | "construction"
  | "facilityService"
  | "wandering";

type TrailLevel = "none" | "trace" | "trail" | "establishedTrail";

interface TrailCell {
  wear: number;
  level: TrailLevel;
  passagesToday: number;
  dominantPurpose: MovementPurpose | null;
  causedByFacilityIds: string[];
}
```

executorは一歩の完了時に`MovementPurpose`と、目的地が施設ならその施設IDをtraffic処理へ渡す。物流、建設、施設利用は強く、目的のない徘徊は弱く記録する。通行量は日次で減衰し、閾値を越えると`trace`、`trail`、`establishedTrail`へ変化する。水上、岩場、建物占有タイルには小道を作らない。

`trail`以上のタイルは移動コストを下げる。A*はそのコストを使うため、人が通った経路が次の経路選択を引き寄せる。ただし、短縮量には下限を置き、遠回りの小道が常に直線経路へ勝つ状態を避ける。

`causedByFacilityIds`は上限付きで主要施設だけを保持する。毎回同じ配列へIDを追加せず、寄与量の大きい施設を安定した順序で選ぶ。

S5で生じるのは未舗装の小道までである。石畳、橋、門、計画道路は、制度投資を扱う後続スライスへ残す。

## 11. シミュレーションの更新順序

1tick内の順序を固定する。

1. 生存割り込み、欲求、制度支持を更新する。
2. 成立制度から未充足の空間需要を生成する。
3. 必要な需要だけ敷地を評価する。
4. plannerが資材、建設、運用タスクを選ぶ。
5. executorが移動と作業を進め、完了した一歩を通行量へ記録する。
6. 規定の時刻に腐敗、交易、配給、維持、小道減衰を処理する。
7. 変更された権威状態をwire protocolへ渡す。

施設の効果を先に適用してから住民を移動させる、といった順序変更は結果を変える。更新順序は統合テストで固定する。

## 12. 観察UI

既存の地図、情報吹き出し、右側inspect panel、tickerを拡張する。新しい全画面管理UIは追加しない。

### 12.1 地図

- 三施設は種類を見分けられるspriteまたは決定論的な図形で描く。
- 建設中は透明度と進捗表示で完成施設と区別する。
- `trace`以上を地面へ重ね、段階に応じて濃さと幅を変える。
- 通行量overlayを切り替えられる。

### 12.2 施設inspect

- 施設種別、制度、稼働状態
- 在庫、容量、当日の利用、維持状態
- 建設を求めた問題、支持者と反対者
- 敷地を選んだ上位理由
- 消費した木材と労働
- 実際に発生した恩恵と負担
- 関連する主要な小道

### 12.3 小道inspect

- 小道段階、wear、当日の通行回数
- 主な移動目的
- 形成へ寄与した施設
- 移動コストの変化
- 最後に利用された時刻

### 12.4 住民inspectとticker

住民には制度支持、施設建設・維持・利用への参加、`rationStrain`を表示する。tickerは需要発生、着工、完成、稼働開始、運用停止、最初の小道化だけを通知し、日常の一歩ごとには流さない。

## 13. 失敗状態と不変条件

失敗は状態として表示し、無言で要求を破棄しない。

| 状況 | 処理 |
|---|---|
| 木材不足 | `awaitingMaterials`を維持し、資源採集を優先する |
| 有効敷地なし | `blocked`理由を保存し、地図変化時に再評価する |
| 施設満杯 | 開拓時備蓄へ退避し、預入を失敗させない |
| 施設へ到達不能 | 到達可能な在庫へ退避し、施設を`blocked`にする |
| 市場に交易路なし | 取引を停止し、資源を生成しない |
| 維持不足 | 施設固有の効果を弱め、状態を表示する |

建物、備蓄、住民、資源タイルは同じ位置を不正に占有しない。完成前の施設は食料効果を出さない。施設ID、需要ID、制度IDの参照切れはwire protocolへ送る前に検出する。

## 14. 決定論と性能

- simから時刻、I/O、`net/`、LLMを参照しない。
- 乱数は注入されたseed付きRNGだけを使う。
- 敷地評価は需要作成時と再評価条件成立時だけ行う。
- 通行量は一歩が完了したタイルだけ更新する。
- 日次減衰は全マップを毎tick走査せず、日境界で処理する。
- protocol updateは変更された施設、需要、trail cellを送る。
- pathfinding用の小道検索は位置indexを使い、施設配列の線形探索を内側loopへ置かない。

10分上限という条件は、デモ専用の強制イベントでは満たさない。共有定数の形成時間、建設費、労働量、通行閾値を調整し、通常シミュレーションの因果を保ったまま到達させる。

## 15. テスト戦略

### 15.1 shared

- 建物union、需要、施設、trail、protocolの型とdecode
- 施設種別と制度種別の全対応
- すべての調整数値が`constants.ts`にあること

### 15.2 server unit

- 制度から需要を一度だけ生成する
- 三施設の候補採点と同点解消
- 木材の受取、運搬、引渡しで総量が保存される
- 完成前に運用効果が出ない
- 穀倉の腐敗抑制と維持不足
- 市場の輸出入、交易路なし、交換上限
- 配給優先順位、節約、`rationStrain`、支持低下
- 一歩ごとの通行加算、目的別重み、日次減衰、段階変化
- 小道による移動コスト低下

### 15.3 server integration

三つの文化・履歴fixtureを用意し、それぞれで次を確認する。

1. 対応制度が成立する。
2. 対応施設が選地される。
3. 木材が搬入され、完成する。
4. 施設が一度以上利用される。
5. 効果と代償が一度以上記録される。
6. 施設に関係する経路が`trail`以上になる。
7. 上記が通常速度10分相当のtick上限内に起き、目安として5分前後に最初の変化が見える。

同じfixtureを二回実行し、重要状態のsnapshotが一致することも確認する。

### 15.4 client

- 施設、建設中表示、trail段階のview modelと描画
- 施設、小道、住民inspectの表示内容
- 通行量overlayの切替
- 施設・小道milestoneのticker順序
- keyboard、touch、狭幅画面で既存inspect操作を壊さないこと

### 15.5 完了ゲート

- `just check`
- `just test`
- 通常速度の公開プレビューで、施設稼働と最初の小道化を確認
- 公開プレビューはLLMを使わない`just serve`を既定とし、観察中にprovider quotaを消費しない

## 16. 実装境界

責務を次の単位へ分ける。

- shared: 型、wire protocol、共有定数
- society: 制度と支持。施設建設の詳細を持たない
- spatial demand: 制度を空間需要へ変換する
- site selection: 候補抽出と採点だけを行う
- construction: 資材搬入と建設状態を進める
- facility operation: 三施設の資源ルールを処理する
- traffic: 一歩を通行量へ変換し、小道を更新する
- pathfinding: 小道の移動コストを読む
- client view model: 権威状態を日本語表示へ変換する
- renderer/UI: 表示と選択だけを担う

`society.ts`、`executor.ts`、`main.ts`へ全処理を足し続けない。既存ファイルが呼出順と境界調整を担い、施設固有ロジックは独立した純粋関数へ置く。

## 17. 受け入れ結果

冬を恐れた住民が共同備蓄を選べば、共同穀倉へ食料と人が集まり、搬入路が濃くなる。交易を選んだ街では市場へ木材と食料が動き、集落入口の往来が伸びる。統制を選んだ街では配給所へ列が生まれ、食料は長持ちするが、待たされた住民の反対が強まる。

三つの街並みはspriteの違いだけではない。在庫、労働、移動、欲求、支持が異なり、その差が同じ地図の上へ残る。
