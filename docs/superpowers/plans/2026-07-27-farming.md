# Farming Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give food a season, so that scarcity recurs before each harvest and institutions form for a reason a player can see.

**Architecture:** A field is a third `Building` member alongside `House` and `Facility`, occupying one tile and reusing the existing construction, depth, shadow, and info-bubble paths. Its crop state advances on season boundaries rather than on a tick timer, so the same seed always renders the same field. Sowing and harvesting are new agent tasks gated to spring and autumn. Berry regrowth flow drops so that foraging alone no longer holds the settlement above the institution threshold.

**Tech Stack:** TypeScript strict (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`), Vitest, Biome, PixiJS 8, pnpm workspaces, `just` task runner.

**Design:** `docs/superpowers/specs/2026-07-27-farming-design.md`

## Global Constraints

- The client owns no game logic. Season comes from `seasonOfTick(world.tick)`, already a pure function in `@agent-town/shared`.
- No `Date.now()` or `Math.random()` anywhere in `sim/`. Simulation randomness comes only from the seeded RNG.
- `sim/` never imports from `net/`.
- Cognitive complexity ≤ 10 per function (Biome). Prefer a new pure module over a longer one.
- Every new sprite path must be added to `SPRITE_PATHS` so `Assets.load` preloads it, with a comment naming what the tile depicts.
- Re-render only through the existing dirty flags in `main.ts`. Do not add a per-frame redraw.
- Row-major grids: `index = y * width + x`.
- UI strings Japanese; code, comments, and commit messages English.
- No absolute local paths in committed content. `npx secretlint .` runs pre-commit.
- Never delete, weaken, or skip an existing test. Baseline to hold: **53 files / 699 tests** — both counts may only go up, never down. Also `just check` 135 files 0 errors, client build 743 modules, `git diff --check` clean.

## Task 3: Crops advance with the season, not with a timer

**Files:**
- Create: `packages/server/src/sim/farming.ts`
- Create: `packages/server/test/farming.test.ts`
- Modify: `packages/server/src/sim/engine.ts`

**Interfaces:**
- Consumes: `Field`, `CropStage`, `isField` from Task 2; `seasonOfTick` from `@agent-town/shared`.
- Produces:

```ts
/** Advances every field to the stage its season implies. Pure: mutates only the fields given. */
export function advanceCrops(world: WorldState, season: Season): void;
```

Growth is driven by season boundaries so that a field's appearance is a function of the world tick and never of elapsed real time or accumulated tick counts.

The transitions:

| From | On season | To | Why |
| --- | --- | --- | --- |
| `sown` | summer | `growing` | the crop takes |
| `growing` | autumn | `ripe` | ready to cut |
| `sown` or `growing` | winter | `fallow` | frost kills an unharvested crop |
| `ripe` | winter | `fallow` | left standing, it rots |

`fallow → sown` is not here. Sowing is work a resident does (Task 5), not something the calendar does for them. Missing the spring window costs the year's harvest, which is what makes farming a wager.

- [ ] **Step 1: Write the failing tests**

These use local helpers you write at the top of the test file, not shared exports:
`worldWithField(stage)` builds a world holding one complete field at a fixed position,
`fieldOf(world)` returns `world.buildings.filter(isField)[0]!`, and `runWorld(seed, ticks)`
generates a world, drives `createEngine(world, new FakePlanner(rng), rng)` forward, and returns
the world. Later tasks reuse the same three names, plus `worldWithCompleteField(stage, tick)`
which additionally sets `world.tick`, `worldWithFieldsPerResident()` which builds a world already
holding `ceil(residents / RESIDENTS_PER_FIELD)` complete fields, `worldWithAgentAt(pos)` which
builds a world with a single resident standing at `pos` and no fields (used by Task 4 to till bare
ground), and one helper per season — `springTick()` / `summerTick()` / `autumnTick()` /
`winterTick()` — each returning a tick inside that season, derived from `DAYS_PER_SEASON` and
`TICKS_PER_DAY`. Put them wherever the existing server tests keep their fixtures and follow that
file's conventions.

```ts

  advanceCrops(world, "autumn");
```

## Task 6: The planner takes up farming

**Files:**
- Modify: `packages/server/src/sim/fakePlanner.ts`
- Test: `packages/server/test/fakePlanner.test.ts`

**Interfaces:**
- Consumes: the three tasks from Tasks 4 and 5, `RESIDENTS_PER_FIELD`.
- Produces: `fieldTasks(world, agent): AgentTask[] | null`, called between `newHouseTasks` and `resourceTasks`.

The current order in `FakePlanner.plan` is priority → house → resources. Insert fields between house and resources. Below housing, because a settlement without roofs should not be farming. Above resources, because sowing and harvesting have season windows and would otherwise lose the window to routine gathering.

Follow the shape of `newHouseTasks`, which returns `null` when there is nothing to do so the caller falls through.

`fieldTasks` decides, in order:

1. If a ripe field exists and it is autumn, harvest the nearest one.
2. If a fallow complete field exists and it is spring, sow the nearest one.
3. If an incomplete field exists, go and till it.
4. If completed fields number fewer than `ceil(residents / RESIDENTS_PER_FIELD)`, pick a site and till a new one.
5. Otherwise `null`.

Reuse the existing site selection used by `newHouseSite`; read it before calling it and keep fields off water, rock, and occupied tiles.

### Step 0: sow and harvest must walk to the field first

Task 5 left `stepSow` and `stepHarvest` treating adjacency as a *condition* rather than as
something to achieve: they check `isAdjacentOrOn(agent.pos, task.pos)` and then call
`finishHeadTask(agent)` unconditionally. A resident standing anywhere else burns the task and
does nothing. The planner would then reissue the same task every tick and the crop would never be
sown or reaped — a livelock, not a visible error.

This must be fixed before `fieldTasks` exists, because `fieldTasks` returns bare `harvest` and
`sow` tasks whose whole premise is that the executor closes the distance.

The codebase already has the pattern to copy. `newHouseTasks` returns a bare `build` task and
`stepBuild` walks to the site itself with `findNearestReachable`; `stepTill` does the same. Sow
and harvest act on a placed field exactly as build and till act on a site, so they follow the same
contract: **the planner names the field, the executor gets the resident there.**

Do this as a bug fix in its own commit, with a failing test first, before touching the planner:

- [ ] Write an executor test placing a resident away from a ripe field in autumn, issuing a bare
  `harvest` task, and stepping until it either completes or a tick budget runs out. Expect the
  stockpile to gain `FIELD_YIELD`. It fails today because the resident never moves.
- [ ] Write the matching test for `sow` in spring.
- [ ] Make `stepSow` and `stepHarvest` walk to the field the way `stepTill` does, keeping the
  season and stage checks at the moment of action — a resident who arrives after the season turns
  must simply fail, not act out of season.
- [ ] Commit as `fix(sim): walk to the field before sowing or reaping`.

The season checks staying at the moment of action is the part to get right. Do not hoist them to
the start of the walk.

**The winter case matters more than it looks.** Task 3 turns a `sown` or `growing` field `fallow` on the first day of winter, and winter is only two days. If the planner could ever sow outside spring, a field sown in winter would be killed the same day it was sown — work spent for nothing, with no visible cause. The season gate in step 2 is what prevents this, so the test below covers all three non-spring seasons rather than just summer. `winterTick` is the load-bearing case; do not drop it because summer already passes.

| regrowth flow | institutions | mean longest pressure | final pop | deaths |
| --- | --- | --- | --- | --- |
| 676/day (today) | 1/8 | 1372/2400 | 4.0 | 0.0 |
| 354/day | 2/8 | 1692 | 4.0 | 0.0 |

- [ ] **Step 1: Write a temporary sweep harness**

- mean final population is **3.8 or above**, so the settlement still grows — but read the note on

- **zero seeds wiped out** — this one is not negotiable
- mean deaths above 0.0 but below 1.0 per run, so starvation is a rare event rather than a routine one
- the pre-harvest trough drops `foodDaysRemaining` below 4 for at least 2400 consecutive ticks in the seeds that form institutions

### What the population number can and cannot resolve

Population is not a continuous measure here, and the threshold above is only meaningful against a
fixed run length. `maybeImmigrate` runs on `world.tick % TICKS_PER_YEAR === 0` and admits **one**
resident per event. `TICKS_PER_YEAR` is `DAYS_PER_SEASON × 4 × TICKS_PER_DAY` = 19,200. The
settlement starts with three residents (`AGENT_NAMES`), and tick 0 can never immigrate because
`hasImmigrationCapacity` needs a completed house first.

So a 36,000-tick run reaches tick 19,200 exactly once and has **a single growth event in its entire
history**. Final population is 3 or 4, less any deaths. "Mean population 3.8" does not describe a
growth curve; it says 80% of seeds took the one immigrant on offer. The 4.000 that saturates the
baseline table is that ceiling, not an equilibrium the food supply chose.

This matters whenever the run length changes. A 76,800-tick run passes tick 19,200, 38,400, 57,600
and 76,800, so it has four growth events and a ceiling of 7 — and "3.8 or above" silently degrades
into "took one immigrant of four available", which is close to free. Score the intent, not the
digits: express the result as **immigration events taken over events offered**, which is
comparable across run lengths. The 3.8/4.0 threshold above is 0.8 of that ratio; at 76,800 ticks the
same bar is a mean population of about 6.2.

## Task 8: Fields you can read

**Files:**
- Modify: `packages/client/src/render/sprites.ts`, `packages/client/src/render/structureLayer.ts`
- Test: `packages/client/test/sprites.test.ts`, `packages/client/test/structureLayer.test.ts`

**Interfaces:**
- Consumes: `Field`, `CropStage`, `isField`.
- Produces:

```ts
/** Ground tile under a field: dry soil when fallow, worked soil once sown. */
export function fieldSoilPath(stage: CropStage): string;

/** Crop drawn over the soil, or null when the field is bare. */
export function cropSpritePath(stage: CropStage): string | null;
```

Tiles, all from the newly vendored `tiny-farm` pack, verified by rendering them at 12× before use:

| Purpose | Tile | Depicts |
| --- | --- | --- |
| fallow soil | `tiny-farm/tile_0000` | a rounded plot of dry soil with soft grass edges |
| worked soil | `tiny-farm/tile_0001` | the same plot in darker, worked soil |
| `sown` | `tiny-farm/tile_0064` | small green sprouts |
| `growing` | `tiny-farm/tile_0065` | taller green shoots |
| `ripe` | `tiny-farm/tile_0066` | golden ears on the stalk |

Tile 0000 was chosen over the full-bleed soil tiles (`0049`, `0050`) on purpose. A full-bleed dirt tile renders an isolated one-tile field as a hard-edged brown square — the same artefact that made forests read as tinted squares before V3 Task 1 fixed it. The rounded plot carries its own grass margin, so a lone field sits on the grass instead of being stamped into it.

That margin only works because of a measured coincidence between the two packs, confirmed by sampling rather than assumed: `tiny-farm/tile_0000` and `tiny-farm/tile_0001` are **fully opaque**, and the grass they bake into their corners is `srgb(132,198,105)` — the exact flat colour of `tiny-town/tile_0000`, the plains tile the map already draws. `tiny-town/tile_0001` (forest) shares the same base green under its tufts. Since `isWalkable` admits only `plains` and `forest`, and `isFreeBuildSite` requires a walkable tile, a field can never be tilled on rock's ochre `srgb(234,165,108)` — which is the one terrain where the baked margin would show as a green halo. The crop overlays `0064`–`0066` are transparent, so they compose over whatever soil is beneath them.

Do not swap either soil tile for one from another pack without re-sampling that corner pixel. The blend is a property of these two specific tiles, not of the packs in general.
