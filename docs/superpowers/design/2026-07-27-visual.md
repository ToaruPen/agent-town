# Visual identity and readability at two scales

Design document for the world map of the real-time nation-ruler game.
Scope: nation identity, territory, city legibility, change, the world↔local transition, and the palette.
Not in scope: HUD/panel layout (`design-hud`), traversal mechanics (`design-traversal`), any game logic.

All colour distances in this document are **CIE ΔE76** computed from sRGB via D65 Lab. ΔE76 overstates
separation in saturated blues, so treat the blue-slot numbers as upper bounds. Thresholds used
throughout: **< 5** indistinguishable, **< 15** effectively the same colour for a viewer comparing
across the map, **≥ 25** confidently distinct for a 2 px stroke, **≥ 40** distinct at a glance.

## Part 1 — Findings about the current visual system

### 1.1 There are two renderers, and the world map is not the Pixi one

The brief states PixiJS as a hard constraint. The world map is **Canvas 2D**:

`packages/client/src/ui/worldMapView.ts:273`
```ts
export function renderWorldMapCanvas(canvas: HTMLCanvasElement, view: WorldMapViewModel): void {
  canvas.width = view.width * WORLD_MAP_CELL_SIZE_PX;
  const context = canvas.getContext("2d");
  ...
  context.imageSmoothingEnabled = false;
```

It is mounted into DOM, not into the Pixi stage — `packages/client/src/ui/worldChronicle.ts:376`:
```ts
const canvasWrapper = element("div", "world-chronicle__map-canvas-wrapper");
const canvas = element("canvas", "world-chronicle__map-canvas");
```

The resident-scale local view is the Pixi one (`packages/client/src/main.ts:96` `new Application()`,
`render/mapLayer.ts`, `render/structureLayer.ts`).

And the current milestone plan explicitly forbids forking the canvas —
`docs/superpowers/plans/2026-07-27-n1-living-nations.md:317`:
> Reuse the existing world-map canvas and chronicle/国柄 renderers. Do not fork them.

**This is a contradiction I cannot resolve by reading, and it is the one decision the owner must make.**
`AGENTS.md:11` says "packages/client — PixiJS renderer", but that describes the package, not this surface.
Per `CLAUDE.md` source-of-truth ordering (AGENTS.md > docs/ > implementation), AGENTS.md wins on intent
and the plan wins on this slice's scope. My design is written so that **the decision does not change any
value in it** (§2.9). Also note "no external asset files" cannot mean literally none — `sprites.ts:138`
loads vendored `/assets/tiny-town/*.png` — so I read it as *no new asset files*, which this design honours:
everything below is `fill`/`stroke`/`arc` primitives.

### 1.3 The measured defect: nation colours already collide, in more than a third of worlds

This is the most important finding in the document.

Nation colour comes from a fixed table of 8 templates, shuffled and sliced —
`packages/server/src/sim/historyGen.ts:187`:
```ts
function createPolities(rng: () => number): MutablePolity[] {
  return shuffled(rng, POLITY_TEMPLATES)
    .slice(0, WORLD_POLITY_COUNT)
```
with `WORLD_POLITY_COUNT = 4` (`constants.ts:79`). The 8 archival colours are deliberately muted, because
they were authored to be washed over terrain at alpha 0.28:

| template | colour | L\* | C\* |
|---|---|---|---|
| 黒貂 sable | `0x6f7f88` | 52.2 | **7.8** |
| 金環 gold | `0xc49a4b` | 66.0 | 47.1 |
| 苔守 moss | `0x708c5a` | 55.0 | 30.5 |
| 河冠 river | `0x5d8fa3` | 56.7 | 19.5 |
| 象牙 ivory | `0xc6bfa2` | 77.2 | 15.7 |
| 灰燼 ember | `0xa65f45` | 47.9 | 37.9 |
| 茨 thorn | `0x8b6b72` | 48.5 | 13.9 |
| 塩湖 salt | `0x879a92` | 61.9 | **8.6** |

Five of the eight are below C\* 20 — near-neutral. Measured pairwise:

```
sable vs river  ΔE 12.6      <- the same colour to a player
sable vs salt   ΔE 13.9
river vs salt   ΔE 18.7
sable vs thorn  ΔE 19.7
```

Composited at the alpha the renderer actually uses (`WORLD_MAP_POLITY_ALPHA = 0.28`), over each terrain,
the **worst pair among the 8 falls to ΔE 3.6–4.2** — below the threshold of perceptibility for flat regions.
Raising alpha does not rescue it: at 0.52 the worst pair only reaches 6.7–7.3.

Enumerating all C(8,4) = 70 worlds the generator can produce:

> **59 % of generated worlds contain a nation pair below ΔE 20. 36 % contain a pair below ΔE 15 —
> two nations a player cannot tell apart.** Worst case ΔE 12.6.

The current territory overlay is therefore not a thing to tune; it is a thing to replace. §2.1 does that
and raises the guaranteed floor to **ΔE 40.9**.

Secondary measured cost, worth knowing: a 0.28 wash of any single colour compresses terrain
discrimination from ΔE 17.0 to 11.8 on the hardest pair (plains vs hills). Tolerable, and it bounds how
high the fill alpha may go (§2.2).

### 1.4 The map is sparse — glyphs are not space-constrained

`WORLD_MAP_CITY_COUNT_MIN = 1`, `WORLD_MAP_CITY_COUNT_MAX = 3` (`constants.ts:95-96`) × 4 polities means
**4 to 12 cities on a 96×64 grid**, plus `WORLD_MAP_CAPITAL_MIN_DISTANCE = 12` and
`WORLD_MAP_CITY_MIN_DISTANCE = 5` guaranteeing separation. City glyphs can be generous and can carry
more than one variable. The binding constraint is cell size, not crowding.

### 1.5 Established idioms this design inherits rather than reinvents

The recent visual work has a consistent taste and I am matching it:

- **Deterministic, position-hashed decoration** — `terrainDecor.ts:51`
  ```ts
  function shouldDecorate(tileX: number, tileY: number, interval: number): boolean {
    return (tileX * 17 + tileY * 31) % interval === 0;
  }
  ```
  and `snowCoordinate` (`:83`) with `Math.imul` mixing, commented *"fixes snow texture across redraws
  while varying neighbouring tiles"*. My contested/changed hatching uses exactly this pattern.
- **Overlay to add light that a multiply tint cannot** — `terrainDecor.ts:88`
  *"A pale overlay can add snow-white light that multiply tint cannot create from green grass."*
  Same reasoning drives the territory wash being a normal alpha fill, not a tint.
- **Alpha as the language of incompleteness** — `structureLayer.ts:24` `CONSTRUCTION_ALPHA = 0.45`,
  applied to every part of an unfinished building. Nation-scale construction reuses the same number.
- **A dark casing under every foreground mark** — `worldMapView.ts:239` strokes every city with `#141b1e`.
  This is what makes glyphs survive any terrain, and §2.2 leans on it hard.
- **A thin progress bar rather than a numeral** — `structureLayer.ts:36`
  ```ts
  .rect(2, 14, 12, 1).fill(0x1d2428).rect(2, 14, 12 * ratio, 1).fill(0xfff176);
  ```
- **A diamond-with-cross as the "you are here" mark** — `worldMapView.ts:245-266` `drawSettlement`.
  §2.6 reuses this for the player's capital instead of inventing a marker.
- **Season expressed as a whole-ground tint** — `sprites.ts:345` `SEASON_GROUND_TINTS`.

## Part 2 — The visual design

### 2.0 The governing principle: identity lives where alpha is 1

A territory fill is a low-alpha wash over terrain, so it can only ever carry a fraction of a colour's
separation. Measured, with the 12-slot ring of §2.1 at fill alpha 0.28, the best case between two nations
over the same terrain is **ΔE 8.4–10.5**. That is enough to see a *seam* where two territories meet; it is
not enough to match a distant region to a nation.

So the design splits identity across channels by the alpha available to them:

| channel | alpha | job | separation available |
|---|---|---|---|
| territory fill | 0.28 | "owned, and this is a different owner from the one next to it" | ΔE 8.4 |
| **territory border** | **1.0** | **which nation** | **ΔE ≥ 40.9 guaranteed** |
| **city glyph** | **1.0** | **which nation, and how big** | **ΔE ≥ 40.9 guaranteed** |
| hatch pattern | 0.20–0.35 | contested / recently changed / beyond-ceiling identity | orthogonal to colour |
| motion | — | *something just changed* only | orthogonal |

The fill number is measured through the **full layer stack** — terrain, then the season wash at 0.10, then
the fill — not banner-over-raw-terrain. The season wash costs about 2 ΔE of terrain discrimination before
the territory fill is even applied, and every fill figure in this document accounts for it. Worst case
across all four seasons and all terrain pairs.

Everything that follows is an application of that table. It also answers the Risk-map problem directly:
the fill stays weak enough that terrain survives, and the map does not become flat blobs because the
information is in outlines and glyphs, which are thin.

### 2.1 Nation identity: a derived banner palette

**Keep `Polity.color` exactly as it is.** It is an archival, lore-bearing value (黒貂 = sable grey-blue,
金環 = gold, 苔守 = moss) authored alongside the founding myth in the same template literal, it is a
server contract the spec says to hold fixed (`spec §5`: 契約維持、フィールド追加も当面行わない), and it
keeps its current job: the 国柄 card accent (`worldChronicle.ts:217` `--polity-color`) and landmark
selection (`historyLayer.ts:58`).

**Add a client-side derived *banner* colour** for every map and ranking use. Banner colours come from a
fixed 12-slot ring, designed for separation at alpha 1.0:

| slot | name | value | L\* | C\* | hue |
|---|---|---|---|---|---|
| 0 | crimson | `0xd34f55` | 52 | 58 | 25° |
| 1 | amber | `0xeea043` | 72 | 62 | 70° |
| 2 | olive | `0x94953b` | 60 | 48 | 105° |
| 3 | jade | `0x68b072` | 66 | 44 | 145° |
| 4 | teal | `0x12968f` | 56 | 34 | 189° |
| 5 | azure | `0x0082bd` | 51 | 40 | 258° |
| 6 | violet | `0x685ea8` | 44 | 44 | 300° |
| 7 | magenta | `0xce68ac` | 58 | 52 | 340° |
| 8 | rust | `0x8a4a22` | 39 | 42 | 50° |
| 9 | moss | `0x557035` | 44 | 36 | 125° |
| 10 | sky | `0x8ecfe0` | 79 | 22 | 225° |
| 11 | plum | `0x512f6b` | 26 | 40 | 310° |

Slots 0–7 are the primaries (min pairwise **ΔE 31.2**); 8–11 are collision fallbacks, chosen to differ
from their hue neighbours on lightness as well as hue (rust L\* 39 vs amber 72; plum 26 vs violet 44;
moss 44 vs olive 60). Min pairwise across all 12 is ΔE 20.8.

Chroma is higher than the archival palette because these are used at alpha 1.0 on thin marks, where high
chroma is legibility, not loudness. The muted archival values remain the right choice for the 国柄 card,
which is a large flat area of colour.

**Assignment rule** — deterministic, and the two properties below are the ones to write tests for:

```
assignBanners(polities: Polity[]): Map<string, number>

  order = polities sorted by descending chroma(polity.color), ties by polity.id ascending
  for each polity in order:
      anchored = chroma(polity.color) >= 18
      candidates = free slots
      separation(slot) = min ΔE76 from slot to every already-assigned slot
      choose:
        1. among candidates with separation >= 26, the one whose hue is closest to
           hue(polity.color) when anchored, else the one with the greatest separation
        2. if none clears 26, the candidate with the greatest separation
      tie-break on lower slot index
```

Two properties, both load-bearing:

1. **It is a pure function of the *generated* polity set, never of the live set.** Feed it
   `history.polities` (fixed at world-gen, `WORLD_POLITY_COUNT` entries, immutable for the session) —
   *not* the list of nations currently alive. If it were fed the live set, a nation dying would free its
   slot and every later claimant would re-pick, recolouring the whole map mid-game. Compute once at
   `welcome`, memoise, never recompute.
2. **Chroma-priority preserves the lore link where the lore link exists.** A colour below C\* 18 has no
   perceptually stable hue — sable at C\* 7.8 and salt at C\* 8.6 are greys whose hue angle is noise — so
   anchoring them to a hue would be meaningless. Letting the neutrals absorb all the drift means the
   genuinely chromatic polities keep their colour: **maximum hue drift among chromatic polities is 12°.**
   金環 stays amber, 灰燼 stays rust, 苔守 stays moss, 河冠 stays sky.

Measured guarantee, enumerating every world the generator can produce (all 1680 ordered draws of 4 from 8):

| generated polities | worst-case min pairwise ΔE76 |
|---|---|
| **4 (`WORLD_POLITY_COUNT` today)** | **40.9** |
| 5 | 39.6 |
| 6 | 36.4 |
| 7 | 33.2 |
| 8 (all templates) | 33.2 |

Against the baseline of §1.3 — worst case 12.6, a third of worlds unreadable — that is the whole point of
the mechanism.

Canonical mapping when all 8 templates are generated:

```
黒貂 sable  -> crimson  0xd34f55   (C*<18, no hue claim)
金環 gold   -> amber    0xeea043   hue drift 12°
苔守 moss   -> moss     0x557035   hue drift  5°
河冠 river  -> sky      0x8ecfe0   hue drift  9°
象牙 ivory  -> plum     0x512f6b   (C*<18, no hue claim)
灰燼 ember  -> rust     0x8a4a22   hue drift  4°
茨   thorn  -> magenta  0xce68ac   (C*<18, no hue claim)
塩湖 salt   -> azure    0x0082bd   (C*<18, no hue claim)
```

The one place lore and separation disagree: 黒貂辺境国 ("sable march") in crimson reads oddly. Provide an
escape hatch — a `POLITY_BANNER_OVERRIDE: Readonly<Record<number, number>>` keyed by archival colour,
empty by default, consulted before the ring walk and excluded from the free-slot pool. **This is a
judgement call to make in the browser, not from a table: put the four archival greys next to their
assigned banners and decide whether the separation is worth the semantic drift.**

**An override preserves the ≥ 26 acceptance bar but not the measured 40.9 floor.** The floor was measured
over the unconstrained algorithm, where chroma-priority chose every slot. Pre-taking a slot by hand removes
that freedom: force 黒貂 → azure and any world that also generates 河冠 (→ sky) sits at **ΔE 29.1**, and two
carelessly chosen overrides can go lower. The greedy then only guarantees "≥ 26 where satisfiable, best
separation otherwise". So the override table is safe but not free, and the way to keep it honest is
mechanical rather than editorial: **V-1's enumeration test must run against the configured override table,
not against an empty one**, asserting a floor the owner declares explicitly. Any override that breaks the
declared floor then fails a test instead of quietly degrading the map.

**Practical ceiling, stated plainly:**

- **≤ 8 nations: full quality**, ΔE ≥ 33 with hue mostly matching lore.
- **9–12 nations: degraded but usable**, ΔE ≥ 20.8 — fallback slots are in play and two blues or two
  purples will be adjacent on the ring.
- **> 12 nations: colour is exhausted.** Add the second channel — reuse the same 12 hues with a
  territory hatch overlay (§2.2), doubling capacity to 24 at the cost of a busier map.
- **> 24: stop using per-nation colour.** Switch the map to *role* colouring — self / ally / rival /
  neutral, four colours — and move identity entirely to hover labels and the ranking table.

None of this binds today: the generator makes exactly 4 from 8 templates. The ceiling matters only if
`WORLD_POLITY_COUNT` is raised, and it can be raised to 8 with no visual work and to 12 with a hatch.

### 2.2 Territory

Layer order, bottom to top. Each row is a separate pass over cells, which is also how
`renderWorldMapCanvas` is already structured (`drawTerrain` → `drawPolityOverlays` → `drawRoutes` →
`drawCities` → `drawSettlement`, `:279-283`):

```
 1  terrain              opaque fill, existing TERRAIN_VIEW colours, unchanged
 2  season wash          whole-map fill, alpha 0.10, season colour            (§2.4)
 3  territory fill       banner colour, alpha 0.28 rival / 0.32 player
 4  contested hatch      diagonal 1px lines, alpha 0.30                       (§2.2.3)
 5  recent-change hatch  diagonal 1px lines, banner colour, alpha 0.35 -> 0   (§2.4)
 6  border casing        1px, 0x141b1e, alpha 0.55, outward — sea/unowned edges only
 7  border               2px banner colour, alpha 1.0, on the cell edge
 8  player inner rule    1px, 0xfff8dc, alpha 0.85, inside the border         (§2.6)
 9  trade routes         existing, unchanged
10  city glyphs          §2.3
11  capital marks        §2.3 / §2.6
```

#### 2.2.1 Fill

Reuse the existing constant unchanged: **`WORLD_MAP_POLITY_ALPHA = 0.28`** for every rival nation. It is
already the right value. Measured through the full stack (terrain → season wash 0.10 → fill), worst case
over all seasons and terrain pairs: terrain keeps **ΔE 9.8**, nations separate by **ΔE 8.4**.

Add **`WORLD_MAP_PLAYER_POLITY_ALPHA = 0.32`** (§2.6): nation separation rises to **ΔE 10.1**, terrain falls
to **ΔE 9.0**. That is the honest ceiling for the fill. 0.36 was the first candidate and does not survive
the full stack — it buys another 1.1 ΔE of separation for another 1.1 ΔE of terrain, landing terrain at
**ΔE 7.9**, which is where hills stop being distinguishable from forest under a blue banner.

Leave **`WORLD_MAP_SELECTED_POLITY_ALPHA = 0.52`** at its current *value* but **change its behaviour**: today
it is a persistent selection, set by `pointerup` and held (`cellAlpha`, `worldMapView.ts:64`, driven by the
handler at `:386-395`). It must become **hover-only and transient**. Full-stack measurement is the reason —
at 0.52 terrain discrimination collapses to **ΔE 6.3**, which is fine for a momentary "which cells are
theirs" answer and not acceptable as a resting state. An implementer who preserves today's persistent
selection inherits that collapse permanently, so this is a behaviour change to make deliberately, not a
value left alone.

Sea cells are never filled, matching `polityIdAtWorldMapPosition` which already treats sea as unowned
(`worldMapView.ts:176`).

#### 2.2.2 Border — the actual identity channel

Stroke only the **outer boundary** of each nation's territory: for every owned cell, draw an edge on each
of its 4 sides whose neighbour has a different owner (or is off-map/sea). Not a per-cell outline — that
would produce the grid, which is the Risk-map failure mode.

```
    cell edge test:  owner(x,y) !== owner(nx,ny)  ->  draw that edge
                     (off-map and sea count as a different owner)

    ┌───────────────┐        each ─ or │ is:
    │ ▒▒▒▒▒▒▒▒▒▒▒▒▒ │          1px casing  0x141b1e a0.55   (outward)
    │ ▒▒▒ nation ▒▒ │          2px banner  <banner>  a1.0   (on the edge)
    └───────────────┘
     interior edges: nothing drawn
```

Widths: **2 px banner + 1 px casing** at the 12 px playable cell (§2.7); **1 px banner + 1 px casing** at
the existing 6 px chronicle cell, where 3 px would eat half the cell.

The casing is not decoration. Measured banner-to-nearest-terrain distances show one slot that cannot
carry itself: `moss 0x557035` is only **ΔE 16.8 from plains `#7d8c62`** — a moss border on plains would
disappear. `olive` (25.8) and `jade` (25.1) are marginal. The 1 px dark casing makes every slot legible
on every terrain regardless of hue, which is exactly what `worldMapView.ts:239` already does for cities.
This is why the ring did not need to be constrained against terrain: the casing decouples them.

Where two nations are directly adjacent, both draw their own edge and the two casings meet, producing a
naturally heavier shared border — correct, since a nation-nation frontier is more significant than a
coastline.

#### 2.2.3 Contested cells

A cell is contested when it is claimed in the live state but its owner differs from the world-history
owner, or (post-N3) is inside an active war zone. Render as a **diagonal hatch**, using the codebase's
deterministic-decoration idiom rather than a stored pattern:

```ts
// hatch a cell when its diagonal band index falls on the stripe
const onStripe = (cx: number, cy: number, phase: number) => (cx + cy + phase) % 4 === 0;
```

Lines are 1 px, at the **contested colour `0xd8cbb0`** (a warm bone that belongs to neither nation and
already has siblings in the palette — it sits between the existing `#f1e8ce` city fill and `#c8b88a`
route colour), alpha 0.30. Both claimants' fills stay underneath, so a contested cell reads as
"someone's, but unsettled" rather than as a third nation.

`phase` is 0 for contested (static). §2.4 reuses the same function with a moving phase for change.

### 2.3 City size and prosperity without numbers

Three variables, three orthogonal encodings, ≤ 12 glyphs on the map (§1.4) so there is room:

```
  city                     capital                  player's capital
                                                    (diamond + cross, reusing drawSettlement)
      ╭───╮                    ◇                          ◈
     │ ███ │                  ◇█◇                        ◇╳◇
      ╰───╯                    ◇                          ◇
   radius = population    shape = capital           the "現在地" idiom
   core   = development   ring   = prosperity
```

**Radius = city population**, 4 tiers, area roughly doubling per tier so the glyph reads as magnitude
(at the 12 px playable cell):

| tier | radius | diameter | area |
|---|---|---|---|
| 1 | 2.5 px | 5 px | 20 px² |
| 2 | 3.5 px | 7 px | 38 px² |
| 3 | 5.0 px | 10 px | 79 px² |
| 4 | 7.0 px | 14 px | 154 px² |

Tier thresholds must be **fixed absolute population values in `shared/constants.ts`**, not percentiles of
the current world. The spec is explicit about this reasoning for the prosperity score
(`spec §4.4`: 正規化は固定の基準値で行い、他国との相対値では行わない — so that another nation dying
cannot move your number), and the same argument applies to glyph size: a city must not appear to grow
because a rival's city shrank.

**Inner core = development level.** A concentric disc in the banner colour lightened toward
`0xfff8dc` by 45 %, radius = `outerRadius * (developmentLevel / maxDevelopmentLevel) * 0.7`. This reads as
a fill gauge — how "full" the city is — with no counting and no numeral. Development 0 is a plain disc.

**Capital = shape, not size.** Capitals are diamonds (the existing `drawSettlement` polygon,
`worldMapView.ts:248-252`), cities are circles. Using shape frees radius to mean population honestly; today
capital-ness is encoded as a larger radius (`WORLD_MAP_CAPITAL_RADIUS_PX = 3` vs `CITY = 2`), which
collides with size.

**Prosperity = capital ring thickness**, 4 tiers: 1/2/3/4 px outer ring, banner colour, drawn outside the
casing. Prosperity is a *nation* quantity, so it belongs on the ≤ 4 capital glyphs, not on every city. Four
rings of differing thickness are comparable at a glance and give the map an honest at-a-glance ranking
without duplicating the ranking table, which is where the numbers live (`design-hud`'s surface).

Every glyph keeps the existing 1 px `0x141b1e` casing (`worldMapView.ts:239`).

**This tier design needs one look in the browser to confirm:** whether ring thickness 1 px vs 2 px is
distinguishable at the chosen cell size, and whether the development core reads as a gauge or as a
smudge on tier-1 cities (radius 2.5 px leaves a core of ~1.2 px, which may be too small — the fallback is
to show development only from tier 2 up).

### 2.4 Change made visible, and kept calm

The calm rule, stated as a budget rather than a feeling:

> **One motion class per event class, motion always decays to a static readable state, and nothing that
> is not changing ever moves.** At any instant the map animates at most: the cells that changed this
> season, plus one season crossfade. Nothing else, ever.

Three kinds of change, three treatments, deliberately different in kind so they never read as one
fireworks display:

**Territory change** — driven by `WorldCellChange { index, polityId }` (`nation.ts:123`). Three phases:

```
 tick 0                     tick 30 (3 s at x1)          tick 300 (season end)
 ┌──────────────┐           ┌──────────────┐             ┌──────────────┐
 │ flash a0.55  │  ──────>  │ hatch a0.35  │  ────────>  │ plain fill   │
 │ new banner   │  decay    │ new banner   │   decay     │ no mark      │
 └──────────────┘           └──────────────┘             └──────────────┘
   "it moved"                "it moved recently"          absorbed
```

- Flash: fill the cell in the new owner's banner colour at alpha 0.55, decaying linearly to the normal
  0.28 over **30 ticks**.
- Then the recent-change hatch (layer 5, §2.2.3 with `phase` advancing) at alpha 0.35, decaying to 0 at
  the next season boundary — i.e. over the remaining ticks of the current season.
- **Stagger by cell index** so a multi-cell conquest ripples instead of strobing:
  `delay = (index * 7) % 12` ticks. Same spirit as `shouldDecorate`'s index mixing.

Lifetimes are in **ticks, not milliseconds**, deliberately: at x8 a season lasts 3.75 s of real time
(`NATION_TICKS_PER_SEASON = 300`, `TICK_RATE = 10`), so tick-based decay compresses with the clock and the
map cannot fall behind itself. This also makes the whole thing a pure function of `tick` — no animation
state to hold, testable in vitest, and identical under either renderer.

**Construction in progress** — **no motion at all.** `ActiveDirective` (`nation.ts:43`) carries
`targetCityId`, so construction is attached to a *city glyph*, not to a cell. Draw a **progress arc** on
the city's casing ring, from 12 o'clock clockwise, 2 px wide, in `0xfff176` — the colour the codebase
already uses for progress (`structureLayer.ts:40`) and route highlight (`worldMapView.ts:225`). The arc
advances once per season resolution, four times a minute at x1. A quantity that changes every 30 seconds
does not need to be animated to be noticed; animating it would spend the motion budget on the calmest
thing on the map.

For a directive with no `targetCityId`, put the arc on the capital.

**Season boundary** — one whole-map crossfade of the layer-2 season wash, **600 ms**, wall-clock rather
than tick-based (it is a UI affordance, not a world event, and must stay legible at x8 where a season is
3.75 s). Colours reuse the established `SEASON_GROUND_TINTS` (`sprites.ts:345`) at alpha 0.10 — a tenth of
the strength used at resident scale, because at world scale the tint's job is only to tell you the season
turned, and it is competing with the territory wash for the same terrain contrast budget:

```
spring 0xe2f2d8   summer 0xf8e6bd   autumn 0xe9bd8f   winter 0xf0f2f4
```

Using the same four values at both scales is the single strongest continuity cue across the scale
transition (§2.5): the season looks the same in both views because it *is* the same constant.

One season boundary every 30 s at x1, affecting the whole map uniformly, is calm by construction — it is a
tide, not an event.

**Deliberately not animated:** score changes, population changes, stability changes, rank changes. All are
continuous quantities that belong to the ranking table and season report. If they pulse on the map, the map
is never still, and then a genuine territory loss has nothing left to announce itself with.

### 2.5 The scale transition

I asked `design-traversal` whether their transition is a continuous camera move or a crossfade; at the time
of writing I have no answer, so this section specifies **what the world view must hand the local view**,
which is the part that does not depend on the answer. Where it does depend, I say so.

Four things must be continuous across the transition. Each is a specific artifact, not a principle:

**1. The banner colour, as a persistent viewport edge band.** A 3 px band in the player's banner colour
along the top edge of the viewport, present in *both* views at the same screen position, never removed.
It is the answer to "whose country am I in", and it survives any transition style because it is not part of
either map. This is also why §2.1's stability property matters: a colour that could change mid-session
would be useless as an anchor.

**2. The footprint rectangle.** Before entering, the world map draws the local map's footprint on the cell
being entered — a 1 px `0xfff8dc` rectangle, alpha 0.9, inset 1 px. On return, the same rectangle appears at
the cell just left and pulses once over 500 ms, then holds statically until the next navigation. This is the
"where was I" anchor, and it is the one thing that makes the return leg not disorienting.

```
   world map, hovering the capital        after returning
   ┌─────┬─────┬─────┐                   ┌─────┬─────┬─────┐
   │     │     │     │                   │     │     │     │
   ├─────┼─────┼─────┤                   ├─────┼─────┼─────┤
   │     │ ┌─┐ │     │  footprint of     │     │ ┌─┐ │     │  pulses once,
   │     │ │◈│ │     │  the local map     │     │ │◈│ │     │  then holds
   ├─────┼─┴─┴─┼─────┤                   ├─────┼─┴─┴─┼─────┤
```

**3. Terrain identity.** The local map's terrain must visibly be the same terrain as the world cell:
entering a `forest` cell must land on a forest-dominant local map. This constrains local-map generation,
not rendering, so it is a note for whoever owns that generator — but if it is violated, no amount of
transition polish will stop the player feeling teleported. The world map's 5 terrains
(`sea/plains/forest/hills/mountains`) and the local map's 4 (`plains/forest/rock/water`,
`TERRAIN_TINTS` in `colors.ts:1`) do not correspond one-to-one; that mapping needs to be authored.

**4. The clock and the season.** The spec is emphatic that the world never stops (`spec §3.3`), so the
year/season indicator must occupy the **same screen position in both views** and the season wash must use
the same four constants at both scales (§2.4). A player who travels into their city and back must be able
to tell, without reading, that two seasons passed while they were down there.

**If the transition is a continuous camera move**, the capital glyph is the natural anchor: interpolate the
camera so the diamond stays fixed on screen and grows, and the footprint rectangle expands to fill the
viewport. This requires the world map to be a Pixi surface — the §1.1 decision. Suggested timing: 450 ms,
ease-out cubic, with the world map's territory fill fading to 0 over the last 40 % so it does not tint the
local terrain.

**If it is a crossfade**, 250 ms is enough, and items 1–4 above carry the continuity entirely. This is the
cheaper path and it works with the canvas as it stands. **My recommendation: build the crossfade first**
— it delivers the whole experience with items 1–4, and it does not force the §1.1 decision before the owner
has seen the map working.

### 2.6 The player's nation versus rivals

The requirement is a genuine tension: find your own territory instantly, without the map becoming a
highlight of one nation. Resolution — distinguish the player **structurally**, not by brightness or motion:

| | rival | player |
|---|---|---|
| fill alpha | 0.28 | **0.36** |
| border | 1 px casing + 2 px banner | 1 px casing + 2 px banner + **1 px `0xfff8dc` inner rule, alpha 0.85** |
| capital | diamond | diamond + **cross-hatch** (`drawSettlement`, `worldMapView.ts:260-266`) |
| motion | none | none |

```
  rival border            player border
  ░░│██                   ░░│██│──
    ^ 1px casing            ^     ^ 1px warm-white inner rule
      ^^ 2px banner
```

The inner rule is the key move. It makes the player's frontier a *double* line — a difference in kind that
the eye finds pre-attentively while scanning, and that survives whatever hue the ring assigned. A rival's
border never becomes a double line, so there is no ambiguity and no arms race of brightness. And because
the player's banner colour is still their own hue, the map does not read as "one special nation and some
others" — it reads as four nations, one of which is drawn with a finer pen.

The 0.28 → 0.36 fill step is small on purpose: measured, it moves nation separation from ΔE 8.4–10.5 to
11.4–12.9, which is enough to bias peripheral vision toward your own territory, and small enough that a
screenshot does not look like a highlight.

**No glow, no animated outline, no permanent pulse on the player's territory.** The reason is concrete:
motion is the channel §2.4 reserved for *change*, and it only works because the map is otherwise still. A
permanently breathing player border would spend that channel on information the player already has, and a
territory loss would then have no way to announce itself.

Instead, an **on-demand locate**: a "find my nation" key (and automatically on entering the world view from
local) pulses the player's border once — inner rule alpha 0.85 → 1.0 → 0.85 with a 1 px outward
expansion, 500 ms, wall-clock. One shot, no loop.

The `WORLD_MAP_SELECTED_POLITY_ALPHA = 0.52` hover state (§2.2.1) applies to *any* nation including
rivals, which is what keeps the design symmetric — the spec's equality principle (`spec §3.5`: 同じ情報公開
範囲) applied to rendering.

### 2.7 Geometry, per surface

The two surfaces have different jobs and therefore different sizes. This is the table the colour work in
§2.1 was missing.

| | chronicle inline map (exists) | playable world map (new) |
|---|---|---|
| purpose | static world-history reference | the board the game is played on |
| cell size | `WORLD_MAP_CELL_SIZE_PX = 6` (unchanged) | **`WORLD_MAP_PLAY_CELL_SIZE_PX = 12`** |
| canvas | 576 × 384 | 1152 × 768, zoomable |
| border | 1 px banner + 1 px casing | 2 px banner + 1 px casing |
| city radii | 2 / 2.5 / 3 / 3.5 px | 2.5 / 3.5 / 5 / 7 px |
| capital ring | 1 px flat (no prosperity tiers) | 1 / 2 / 3 / 4 px |
| development core | omitted — no room | shown from tier 2 up |
| hatch period | every 3rd diagonal | every 4th diagonal |
| change animation | none | §2.4 |
| live territory | N1 only, then static (see §5) | yes |

At 6 px cells the map is a thumbnail and honest about it: territory fill, 1 px borders, capitals vs cities,
nothing else. Trying to fit prosperity rings and development cores into 6 px would produce mud. The
degradation rule is simply **drop channels in reverse order of importance** (development core, then
prosperity ring, then hatch), keeping fill + border + glyph size at every size.

12 px is the recommended playable cell: 1152 × 768 fits a desktop viewport at 1:1, a 3 px border assembly
is a quarter of the cell so terrain still shows, and the tier-4 city at 14 px diameter overflows its cell
slightly — which is correct and already true today (`CAPITAL_RADIUS_PX = 3` on a 6 px cell is exactly the
cell). **16 px is the alternative if the prosperity rings prove indistinguishable at 12 px**; it costs a
1536 × 1024 surface and requires panning on smaller screens.

## Part 5 — Implementation slices, in order

Each slice is independently visible in a browser and independently testable.

**V-1 — Banner palette.** `render/nationBanner.ts` and the `colors.ts` additions. Tests: assignment is
deterministic for a given polity list; identical for a permuted *live* list (the §2.1 property 1 guard);
every generated 4-of-8 draw yields min pairwise ΔE ≥ 40; chromatic polities drift ≤ 12°; the override table
is honoured and its slot is excluded. Wire it only to the ranking-table swatches and the existing city
dots. *Nothing else changes* — this slice is worth landing alone because it fixes a defect that exists
today, independent of everything below.

**V-2 — Territory border and casing.** Edge extraction in the view model, painted at 6 px on the existing
chronicle canvas. Tests: interior edges are not emitted; sea and off-map count as different owners; a
single-cell nation emits 4 edges. Visible result: the current territory blobs get outlines, and the map
stops being a wash. *Look for: whether 1 px + 1 px is enough at 6 px cells, and whether the moss/plains
case is genuinely rescued by the casing.*

**V-3 — City tiers.** Population radius, capital-as-diamond, development core, prosperity ring. Tests:
tier boundaries are absolute; a rival's collapse does not change your city's tier. *Look for: whether ring
thickness 1 vs 2 px separates, and whether the development core survives at tier 1.*

**V-4 — Player distinction.** Fill 0.36, border inner rule, capital cross-hatch, on-demand locate pulse.
Tests: exactly one nation is drawn with the inner rule; when `playerNationId` is null none is. *Look for:
does the map still read as four nations, or as one highlighted nation and three others? This is the
judgement I cannot make from a table.*

**V-5 — Change.** `WorldCellChange` flash and decay, the recent-change hatch, contested hatch, construction
arc, season wash crossfade. Tests: phase is a pure function of `tick` (same tick → same frame); decay
reaches zero exactly at the season boundary; stagger spreads a 10-cell change across ≥ 8 ticks; at x8 the
compressed lifetimes still complete. *Look for: at x8 with a war running, is it a map or a fireworks
display? If the latter, the first thing to cut is the recent-change hatch, keeping only the flash.*

**V-6 — The playable surface at 12 px** and the scale-transition anchors (edge band, footprint rectangle,
shared clock position). This is the slice that forces the §1.1 renderer decision, and it is last on purpose:
by then the owner will have seen every value in this document rendered and can judge whether a continuous
camera move is worth moving the world map into Pixi.

## Part 6 — Risks, and what I could not settle from reading

**Blocking on someone else's decision:**

1. **Canvas 2D vs PixiJS for the world map (§1.1).** A real contradiction between the brief, `AGENTS.md:11`,
   and `plans/2026-07-27-n1-living-nations.md:317`. Does not affect any value here, but decides whether
   the §2.5 transition can be a camera move. Needs the owner.

2. **The protocol does not exist yet (§1.6).** Two concrete asks for whoever writes it:
   - **`ActiveDirective` cannot yield a progress fraction.** It carries `seasonsRemaining` (`nation.ts:48`)
     but not the total; the total lives on `DirectiveOption.seasons` (`nation.ts:39`), which is a
     *candidate* list the client may not receive for rival nations. The construction arc of §2.4 needs
     either the total seasons on `ActiveDirective`, or an explicit `progress: number` (0..1). I did not
     guess which.
   - **`WorldCellChange` needs to reach the client as a per-season delta**, not be recomputed by diffing
     snapshots. If the client has to diff, a dropped or coalesced update silently loses a flash.

3. **`design-traversal`'s transition style.** Asked, unanswered at time of writing. §2.5 is written to be
   correct either way, with the camera-move variant marked as conditional.

**Risks I own:**

4. **Fill alpha 0.28 gives only ΔE ~9 between nations.** This is by design (§2.0) but it is the design's
   main bet: that borders and glyphs carry identity well enough that the fill need not. If it turns out
   players still try to read territory by fill colour alone, the lever is the hatch — give each nation a
   hatch period from a small set (3/4/5/none) as a second fill channel, at the cost of a busier map.
   **Judge in the browser: can you tell two non-adjacent territories apart without looking at a border?**

5. **黒貂 → crimson (§2.1).** The four near-neutral polities get whatever separation demands, and some
   results will read as semantically wrong. The override table is the fix, but which cases need overriding
   is an authorial call requiring a look at all eight banners against their names.

6. **The 12 px cell is unvalidated.** Every glyph size in §2.3 is derived arithmetically, not seen. If the
   prosperity rings do not separate, the fallbacks in order are: 16 px cells, then 3 prosperity tiers
   instead of 4, then move prosperity off the map entirely to the ranking table.

7. **ΔE76 flatters blues.** `azure 0x0082bd` and `sky 0x8ecfe0` are 29.1 apart by ΔE76 and would be closer
   under ΔE2000. They are ring slots 5 and 10, so both are in play only at ≥ 6 nations. If the ring is ever
   used near its ceiling, re-run the separation check under ΔE2000 before trusting slots 8–11.

8. **A 96 × 64 = 6144-cell full redraw per frame** is trivial in Canvas 2D but wasteful in Pixi if built as
   6144 `Graphics` objects. If the map moves to Pixi, territory fill and borders should be **one `Graphics`
   per nation** (a single path with many sub-rects), not one per cell. The existing `drawWater` /
   `drawSnowSheet` in `terrainDecor.ts` already use exactly this one-`Graphics`-many-rects pattern, so the
   idiom is established.

9. **Contested cells have no contract.** §2.2.3 defines "contested" as live owner ≠ world-history owner,
   which is inferable from data that exists. Anything richer (active siege, disputed claim) waits for N3's
   war model and should not be designed now.
